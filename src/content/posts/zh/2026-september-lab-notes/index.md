最近整理博客时，我想把散落在代码仓库、服务器和证书文件夹里的事情放到一起，给这一阶段留一份记录。

算法训练是其中的一条线：做题、参加比赛，再把解法整理成自己能讲清楚的笔记。另一条线是把日常要用的工具放到自己的环境里，从部署、配置开始，遇到具体问题就继续查代码、做修改，有些修改最后也提交回了上游。

这篇记录以 **2026 年 9 月 22 日** 的仓库、PR 和服务器状态为准。之后项目会变化，留下当时为什么做、做到了哪里，比单纯列一个项目名更有意义。

## 算法训练：让做过的题留下可回看的东西

暑假做过一批强连通分量、割点割边、双连通分量和差分约束相关的题。整理时，我先把 SCC 缩点、拓扑排序和 DAG 上的处理单独写成了[第一篇刷题记录](/zh/posts/summer26-1-scc/)。这篇文章已经合并到博客仓库并发布。

写题解给我的一个要求是：除了记住代码，还要把“为什么可以这样建图”“缩点后保留了什么”“哪些边界情况不能省略”讲明白。接下来可以继续沿着这个方式，把割点割边、双连通分量和差分约束分别整理。

做题之外，我也在整理承载这些记录的工具。

### 博客、代码和做题记录如何放在一起

[xw7qwq](https://github.com/xw7qwq) 是存放这组个人项目的 GitHub 组织。几个项目负责不同的数据，博客把其中适合阅读的信息呈现出来。

| 项目 | 我用它记录什么 | 当前与博客的联系 |
| --- | --- | --- |
| [nfuwari](https://github.com/xw7qwq/nfuwari) | 文章与学习笔记 | 基于 Astro 和 Fuwari，构建后发布到 GitHub Pages |

| [MacFlare](https://github.com/xw7qwq/macflare) | Mac 上的应用与音乐状态 | 通过公开 API 为博客顶部提供应用图标和音乐信息 |

文章走的是 Markdown、Astro 构建、GitHub Pages 发布这条路径；域名由阿里云 ESA 提供边缘分发。应用状态和刷题数据则在浏览器里向各自的公开 API 请求。CodeFlare 目前是独立的源码站点。更具体的网站结构放在[关于页面](/zh/about/)。

这里有两个我希望保留的区别：**提交记录和源码归档是不同的资料；一份代码也不等于一道已经通过的题。** 比如 OJFlare 贡献图按 UTC+8 统计每道题的首次 AC，而代码仓库还可能包含模板、尝试和未完成的代码。把这些语义区分清楚，记录才有参考价值。

## VPS：一台持续维护的个人工具箱

我通过 SSH 重新看了一遍服务器。当天能确认的是 19 组 Docker Compose 项目、34 个运行中的容器，以及一些由 systemd 或独立进程管理的服务。它们涵盖评测、邮件、笔记、数据看板、同步和监控。

这些服务大多建立在现有开源项目上。我在自己的环境里部署、配置，并围绕实际需求做适配；其中一些改动还留在本地。具体哪些修改提交回了上游，放在后面的 PR 记录中单独说明。

### 从做题到维护评测环境

和算法训练最接近的是 [DMOJ](https://github.com/DMOJ/site)。当前部署包含网页、后台任务、通信桥、评测机、数据库和缓存，另有 PDF 服务与 HDU 特殊评测适配服务。

一次提交要经过几个环节：网页接收代码，任务进入评测链路，评测机在对应环境中运行程序，再把结果交回网站。网页展示的一个 AC，背后涉及提交状态、运行环境、资源限制和结果存储。

这套部署的本地修改涉及比赛计分、排名可见性和提交界面等部分，HDU SPJ 也有单独的适配。题目搬到自己的评测环境后，输入输出约定、checker 的行为、编译环境和评分规则都要对得上。这些细节与平时只在现成 OJ 上提交代码的体验很不同。

目前能据代码和运行进程确认这些组件与改动存在；这次没有重跑整套评测测试，也没有逐题验证全部题库。对我来说，后续值得继续整理的是“怎么证明一道导入题判得对”，把普通样例、边界输入和特殊评测的验证方法留下来。

### 邮箱：把服务、协议和界面接起来

另一组服务是 Stalwart 邮件服务端和 [Bulwark Webmail](https://github.com/bulwarkmail/webmail) 网页客户端。我的部署使用带本地修改的 Bulwark，包括按域名组织文件夹、JMAP 交互和 Passkey 登录相关适配。

这类工具把前端和后端之间的关系变得很具体：界面上的文件夹要对应到邮件数据，登录状态要贯穿后续请求，操作失败也需要能在页面上解释。可用的服务既需要界面，也需要协议和状态保持一致。

这里记录的是自己的部署版本。上游项目、服务器上的本地改动和已经合并的贡献是三种不同的状态，之后升级时也需要分别追踪。

### 个人数据、笔记和日常信息

FitBaus 在服务器上提供 Fitbit 数据看板和只读 API；Fast Note Sync 则与 Obsidian 插件配合，处理笔记和附件同步。前者让我接触到数据展示和接口设计，后者更直接地涉及多端状态、附件和同步失败后的处理。

RSSHub、OpenList、TaoSync 等工具负责信息获取、文件入口与同步。放到一起看，这些服务的共同问题是：数据从哪里来，如何更新，更新失败时旧数据是否还能使用，以及怎样知道上一次成功发生在什么时候。

个人记录里只保留这些工具的作用和结构，实际邮件、笔记、健康记录和账号配置仍留在自己的环境里。

### 多人同步与前后端适配

服务器上还运行着 [DreamStream99](https://github.com/ypnomania/DreamStream99)，它把 Win98 风格的静态前端与房间同步、媒体处理服务分开。一起观看视频时，播放、暂停、跳转和重新加入房间都会改变状态，需要考虑权限、重复操作和多个客户端之间的时序。

另一组 NeXus / Xboard 相关部署包含前端、同源中间层和既有后端。中间层负责把浏览器发出的明确操作映射到后端接口。这些实践与后面提到的 EZ-Theme 接口兼容工作有关：前端要知道后端实际支持哪些行为，而不能只靠页面上出现了一个按钮来判断。

DreamStream99 和 EZ-Theme 都有我已经合入上游的 PR。不过，PR 合并记录不能自动证明服务器当前运行的镜像就包含所有后续修改，部署版本仍然要单独检查。

## 从本地修改到上游 PR

我的 GitHub 账号是 [theLucius7](https://github.com/theLucius7)。除了维护自己的仓库，也会把使用开源项目时遇到的问题整理成 PR。下面这些都已经由上游合并，日期按 GitHub 记录的 UTC 日期列出。

### QQ Chat Exporter：认证、任务状态和有界查询

在 [QQ Chat Exporter #675](https://github.com/shuakami/qq-chat-exporter/pull/675) 中，我补齐了 WebSocket 的访问令牌传递。HTTP 请求完成认证后，实时进度和流式搜索的 WebSocket 连接也需要带上当前令牌，重新连接时同样如此。浏览器访问入口使用 HTTPS 时，对应的 WebSocket 地址也要正确使用 `wss`。

随后是 [#677](https://github.com/shuakami/qq-chat-exporter/pull/677)：把实验性的私聊漫游查询接进现有导出流程。它在 **2026 年 9 月 6 日** 合并。

这次改动串起了一条完整的用户路径：

1. 从已有私聊会话进入；如果只有 QQ 号，先查找得到 `peerUid`，再进入漫游导出。
2. 填写起止日期。
3. 服务端创建任务，在限定范围内发现锚点并查询消息。
4. 将恢复的数据送入现有解析、资源处理和格式导出流程。
5. 在任务页查看进度、取消任务或下载结果。

真正需要仔细处理的部分包括查询预算、任务排队、取消、状态恢复，以及结果应该怎样解释。日期跨度、消息数量、序号查询和并发都有边界；历史查询还要经过独占门控，避免互相干扰。

**完成一次有限范围的扫描，不等于证明云端历史完整。** 缺少可信锚点、达到预算或遇到异常时，需要保留 `partial` 和停止原因；即便 `partial=false`，也只表示算法完成了它定义的扫描范围。代码中的 `serverCompletenessProven` 始终是 `false`。这个功能针对私聊，依赖已登录的 QQ 和可用的桥接能力，不能外推成任意会话的完整历史恢复。

这也是这次贡献里值得写下来的部分：接口除了返回数据，还要把它能证明什么、不能证明什么说明白。

## 接下来继续做什么

这些事情最终又会回到几个具体的动作上：把做过的图论题整理成能解释清楚的文章；把服务器上的本地改动、升级与恢复过程留下来；遇到可以独立说明和验证的问题时，继续向上游提交小而完整的 PR。

比赛结果、合并记录和运行中的服务都是这一阶段的产物。下一次回看这篇记录时，我希望还能顺着文章找到代码、数据来源和验证过程，知道自己当时做了什么，也知道哪些地方还需要继续补上。
